Layer 2 — Environmental & sensor data

Layer 3 — Infrastructure & logistics
Traffic maps & congestion data Public transport status feeds Hospital capacity / readiness feeds Utility company alert feeds
Per-signal scoring dimensions (required)
Source credibility score
Verified official vs. anonymous social post. Official sensors score higher than anonymous tweets.
Geolocation confidence
How precisely can the signal be located? GPS-tagged vs. vague neighborhood reference.
Urgency language score
NLP-assessed intensity of language used in the signal. "Water entering homes" vs. "street looks wet."
Mention velocity
How fast is this signal spreading? Spike in posts over 5 minutes = higher urgency weighting.
Contradiction level
Does this signal contradict other concurrent signals? Conflicting signals must be flagged before action.
Low-confidence or suspicious signals must be flagged and held for verification — they must NOT directly trigger emergency actions without escalation logic.
03
All problem statements
The 5 core tasks the agentic system must accomplish
PDF 1 — Problem statement section
PS-1 Multi-source signal ingestion & fusion
Ingest and fuse at least three signal sources — social posts, weather, traffic, emergency calls, mock sensors, field reports, and/or historical data — into a single unified, real-time crisis picture.
PS-2 Crisis detection & classification
Detect and classify each crisis by: type, location, severity level, confidence score, affected population size, expected duration, and likely evolution path over time.
PS-3 Constrained resource prioritization & allocation
Prioritize and allocate constrained response resources across one or more simultaneous crises. Show the optimization logic and explicit trade-offs when resources are insufficient for all needs.
PS-4 Coordinated response simulation
Simulate coordinated actions such as traffic rerouting, emergency dispatch, hospital preparation, utility escalation, and public alerts. Show the predicted impact of each action.
PS-5 Outcome prediction & error recovery
Predict outcomes, side effects, and unintended consequences for each response action. Handle false positives, false negatives, and conflicting signals through verification and escalation logic — including ability to retract alerts.

05
All enhanced system requirements
10 advanced capabilities — these define the depth expected in a competitive submission
PDF 1 — Enhanced system requirements
ER-1 Multi-signal fusion
Use at least three signal source types simultaneously: social media/citizen posts, weather, maps/traffic, emergency call frequency, mock sensors, public transport status, or historical vulnerability maps. All must be fused into a unified incident model.
ER-2 Source credibility & misinformation handling
Score each incoming signal on all five dimensions: source credibility, geolocation confidence, urgency language, mention velocity, and contradiction level. Flag low-confidence or suspicious signals before they trigger any actions.
ER-3 Crisis classification
Classify crisis type — flood, heatwave, accident, infrastructure failure, power outage, protest, or disease cluster — with an attached severity level and confidence score for each classification output.
ER-4 Severity & evolution prediction
Estimate all of the following: affected radius, affected population count, expected duration, peak impact time, spread risk, and an uncertainty range for every prediction made.
ER-5 Resource allocation optimization
Model constrained resources: ambulances, police units, rescue teams, shelters, generators, water tankers, field teams, drones. Allocate based on impact severity, urgency, travel time to site, and real-time resource availability.
ER-6 Multi-crisis coordination
Handle at least two simultaneous incidents. Explicitly show the trade-offs in prioritization and resource assignment when both incidents compete for the same constrained assets.
ER-7 Impact simulation
For each planned response action, show all of: before-state → response action taken → expected after-state, response time improvement achieved, congestion impact, resource cost, and any possible side effects of the action itself.
ER-8 Stakeholder notification
Generate tailored alert messages for all six stakeholder groups: the public, emergency services, hospitals, utility companies, transport authority, and media/command center. Each must receive different language, detail level, and call-to-action.
ER-9 False positive / negative handling
Simulate a false alarm, an early low-confidence signal, or conflicting signals — and demonstrate the system's ability to verify, escalate, correct, or retract the alert with a full correction notification sent to stakeholders.
ER-10 Robustness & degraded-mode operation
Handle all of the following gracefully: API downtime, stale or missing data, missing geolocation, duplicate incident reports, and rate limiting — using fallback data sources or manual escalation paths when primary signals fail mid-response.

Stage 1 — Multi-source input
Ingest ≥3 signal streams at once. Score credibility of each. Flag contradictions between sources. Begin fusing all inputs into a unified, deduplicated event model.
Stage 2 — Crisis detection
Output: incident type, location, confidence score, estimated affected population, and any conflicting hypotheses (e.g., "flooding" vs. "water main burst" as competing explanations for the same signals).
Stage 3 — Severity prediction
Output: affected radius, likely duration, peak impact time, geographic spread risk, and an uncertainty range. These directly feed the resource allocation step.
Stage 4 — Resource allocation
Inventory available constrained resources. Run the optimization. Assign resources across simultaneous incidents. Output the allocation plan and explicitly show what was deprioritized and why.
Stage 5 — Simulated response (coordinated actions)
Execute these simulated actions: reroute traffic, create and dispatch emergency tickets, alert hospitals to prepare for intake, escalate to utilities, push tailored public notifications per stakeholder group.
Stage 6 — Impact visualization
For every action taken, show: before/after state, response time delta, congestion change, resource cost incurred, and any unintended side effects introduced by the response itself.
Stage 7 — Recovery / correction
When field verification contradicts initial classification: update the crisis model, retract or revise the relevant alerts, send correction notifications to all affected stakeholders, and log the full audit trail of what changed and why.
Antigravity internal workflow (also demanded — PDF 2)
Within Antigravity, the agent must produce and expose: workplan, task plan, agent observations, reasoning, decisions, tool calls made, action execution logs, error recovery steps, and final outcomes — all as inspectable traces.
07
All simulations & the official example scenario
The full dual-crisis example from the document, stage by stage
PDF 1 — Example scenario
INPUT SIGNALSWhat enters the system
Social media posts report flooding in area G-10. The weather API confirms heavy rainfall. The traffic API shows a congestion spike in the same zone. One field report contradicts — it suggests a broken water main rather than actual flooding. Simultaneously, and independently, a heat emergency is reported in a nearby low-income neighborhood.
DETECTION OUTPUTWhat the system classifies and surfaces
Classifies the G-10 incident as probable urban flooding with a confidence score. Separately identifies the conflicting water-main hypothesis and flags it as requiring field verification before the response plan is locked. Independently classifies the heat emergency in the low-income neighborhood with its own severity score and affected population estimate.
PREDICTION OUTPUTWhat the system estimates
Estimates affected zones for both incidents. Predicts likely duration of each, congestion spread path, and vulnerable population risk — particularly noting that residents in the low-income neighborhood may lack access to cooling, elevating the heat emergency's severity.
RESOURCE ALLOCATIONHow limited resources are split across two live crises
Prioritizes rescue teams and police traffic units for G-10 (flooding, higher area impact). Assigns medical outreach teams to the low-income neighborhood heat emergency. Allocation decisions are based on severity scores and resource constraints — the trade-offs are output explicitly so the operator can see exactly what was deprioritized.
SIMULATION (ACTIONS TAKEN)Coordinated response executed
Reroutes traffic away from G-10. Creates an emergency dispatch ticket. Sends a public alert. Notifies the hospital to prepare for intake. Updates the incident command dashboard. Simulates the resulting effect on response time and overall congestion levels, including any side effects.
RECOVERY / CORRECTIONWhen the initial classification was wrong
Field verification confirms only a water-main burst — not widespread flooding. The system updates the classification. Retracts the public flood alert. Sends a correction notification. Notifies the utility provider to address the burst. Logs the full correction with an audit trail of what changed, why, and which stakeholders were re-notified.
What each simulation output must contain (ER-7)
Before-state
What the situation looked like before the response action was executed.
Response action
The specific action taken: dispatch, reroute, alert, escalate, etc.
Expected after-state
Predicted state of the incident and infrastructure after the action takes effect.
Response time improvement
Quantified delta in how quickly responders or resources reach the scene.
Congestion impact
Effect of the action on traffic flow and public movement in the affected area.
Resource cost
What resources were consumed or tied up by this action.
Possible side effects
Any unintended consequences — e.g., rerouting creating congestion elsewhere, alert causing panic.

09
All stakeholders — who gets notified, how differently
6 distinct audiences each requiring a tailored message with different language, detail, and call-to-action
PDF 1 — ER-8 Stakeholder notification
General public
Evacuation instructions, areas to avoid, emergency contact numbers, nearest shelter locations. Plain language — no technical jargon. Staged alerts to avoid panic-induced congestion. Retraction messages if a false alarm is corrected.
Emergency services (includes police units, rescue teams, fire, paramedics)
Dispatch coordinates, severity classification, specific resource assignment, estimated arrival corridors, suggested routes. Real-time updates as the situation evolves. Police traffic units receive routing instructions and blockade coordinates.
Hospitals
Expected patient surge estimate, injury type profile (flood injuries, heat exhaustion/stroke, trauma), required readiness level, estimated ETA of incoming cases, specific ward preparation needed.
Utility companies
Escalation alert for power, water, or sewage infrastructure at risk or already compromised. Repair priority level, affected grid zones or pipeline segments, estimated duration of impact, and utility-specific action items.
Transport authority
Rerouting instructions, affected transit lines, road/bridge closures, estimated clearance time, staging area coordinates for transport-based evacuation support.
Media / command center
Incident summary, current confidence level, actions taken, current resource deployment status, predicted crisis evolution, and press-ready briefing language for public communication.
Police as a stakeholder: police units are explicitly listed as emergency response resources (ambulances, police units, rescue teams…). For notification purposes, police fall under "emergency services" — which is one of the 6 stakeholder groups. The system must send them dispatch coordinates, assignment details, and real-time updates.
10
All recommended stress-test scenarios
4 failure modes the system must survive and demonstrate
PDF 1 — Recommended stress-test scenarios
Scenario A — Resource war
Two or more crises occur within 30 minutes and compete for the same limited emergency resources. The system must break the tie based on optimization logic, clearly show what was deprioritized and why, and adapt in real time if one crisis escalates.
Scenario B — Sensor blackout
Social media indicates flooding but official sensor data is unavailable or directly contradictory. The system must show how it handles high-velocity, low-confidence social signals without official confirmation — avoiding both dangerous over-reaction and dangerous inaction.
Scenario C — Mid-response API failure
A data API (weather, traffic, or sensor) fails while a crisis response is already in progress. The system must fall back to cached or alternate data sources and continue operating — not stall, crash, or silently degrade without notification.
Scenario D — Alert backfire + false alarm correction
A public evacuation alert causes evacuation congestion that worsens the crisis itself. The system must detect this side effect and trigger staged re-alerting or rerouting. The scenario then requires a full false alarm correction cycle: apology/retraction message, updated classification, and a log update with full audit trail.

14
Judge's checklist & final notes
What judges will look for, and what will get your submission immediately rejected
PDF 2 — Final notes for participants
✓ The system must observe, reason, decide, act, evaluate, and adapt
Judges are explicitly looking for all six behaviors in the agent loop. A system that only executes predefined branches does not qualify — even if it produces polished output. Every trace should show the agent observing new information, updating its reasoning, and making decisions it couldn't have made without that new information.
✓ Baseline comparison is mandatory and must be demonstrable
Show that your agentic system outperforms a simple heuristic or non-agentic approach on at least one measurable dimension (speed, accuracy, resource efficiency, or coverage). Include this in both the demo and the README.
✓ At least one failure / edge case must be live-demonstrated
Robustness evidence is not optional. You must demonstrate at least one of: API failure mid-response, contradictory data handling, missing geolocation, duplicate incident de-duplication, or a false alarm correction — and show how the system recovers without manual intervention.
✓ Use realistic mock data if real APIs are unavailable
Clearly label all synthetic data as synthetic. Do not include personal or sensitive information in any mock datasets. Judges accept mock data — they do not accept unlabeled mock data.
✓ Reliable end-to-end workflow over broad-but-broken ambition
A solid, complete pipeline on a narrower scope beats an ambitious system that fails or skips stages mid-demo. Build the full end-to-end loop first, then add breadth. Judges reward depth and reliability over coverage and claims.
✕
Immediately disqualifying — do not build any of these and call it "agentic": A simple summarizer. A listing or feed app. A static dashboard. A fixed-rule engine. A hard-coded workflow. Any system that executes predetermined branches without genuinely reasoning about new inputs. Judges will identify and reject these. The test: if the system's behavior doesn't change when it receives new or contradictory information, it is not agentic.
